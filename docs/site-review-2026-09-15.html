The editorial system underneath this site is unusually strong: a tag allowlist that gates the build, an orphan-link auditor, documented post archetypes, cover image and alt text on 100% of posts, zero em dashes. Both existing audit scripts pass clean. What follows is what those scripts don't look at.

Broken 9 findings · 5 fixed

Things that are wrong right now, on the live site or in the build.

/blog/, /posts/, /articles/, /showcase/ and /docs/ all redirect to /space/

Fixed

Every section's _index.md carried the same copy-pasted alias list. Hugo let one page win the collision and space won it. /blog/ is the single most-guessed URL on a blog, and it landed people in rocket launches.

Wascurl https://jamesm.blog/blog/ → <meta http-equiv="refresh" url=https://jamesm.blog/space/>

FixedRemoved posts, articles, blog, showcase, docs from all 12 section index files. Kept only the real ones: web3→blockchain, data→data-engineering, idea→ideas. Also dropped the self-aliases ("ai" on content/ai/_index.md) and the two containing spaces. Verified with a clean rebuild: the five junk paths resolve to nothing, the three genuine aliases still redirect correctly, and every section page renders unaffected.

Performance 5 findings · 2 fixed

Two of these dominate everything else: images and the search index.

The homepage shipped 5.39 MB of cover images for ten posts

Fixed

Cover images live in static/, which bypasses Hugo's image pipeline entirely — no resizing, no format conversion, no srcset. They were served at their native 1280–1792px into a 670px slot, roughly 2.5× oversized.

WasHome page 1: 5.39 MB · /ai/ page 1: 4.87 MB · /music-production/: 3.35 MB
254 JPG + 95 PNG, zero WebP or AVIF
mac-mini-m6-hermes-agent-infographic.png = 1.9 MB · game-technology-2026.png = 1.2 MB
FixedLower-risk fix than the full pipeline rework: resized and recompressed in place, same paths and filenames, zero frontmatter changes across 350 posts. JPEGs capped at 1600px long edge and re-encoded (quality 82, progressive) - 85 files, 28.5 MB → 14.0 MB. PNGs run through pngquant (quality 75-95) - along the way, found 30 files with a .png extension that were actually JPEG-encoded (real magic bytes checked); routed those through the JPEG path instead, writing back to the same .png-named path. static/assets/images/ total: 46 MB → 24 MB (48%). Homepage: 5.39 MB → 2.68 MB for more posts (15 vs 10, after the pagination fix). Verified: zero corrupted files across all 137 images, and visually spot-checked two text-heavy infographics at full size - fully legible, no visible artifacting.

Search downloaded 963 KB before you could type a character

Fixed

/index.json embedded the full body text of all 350 posts.

Was3.65 MB raw / 963 KB brotli · 2.76M characters of post body
FixedAdded layouts/_default/index.json, a project override of the theme's index template, truncating the content field to 600 characters per post instead of the full body:
"content" (.Plain | strings.Truncate 600)
350 entries, raw size 3.6 MB → 1.1 MB (gzip -9: 232 KB, so brotli should land lower still). Verified functionally, not just by file size: served the rebuilt site locally and ran a real search for "iceberg" through the live Fuse.js index - the three actual Iceberg posts now rank at the top, matching or improving on the pre-fix ranking.

No cache headers on HTML at all

High

Every HTML response comes back with no cache-control, so Cloudflare classifies it as dynamic and never serves it from the edge. For a fully static site this is the cheapest available win.

EvidenceGET / and GET /ai/ai-evals-are-broken/ → no cache-control, cf-cache-status: DYNAMIC
FixA Cloudflare cache rule for text/html with a short edge TTL and origin revalidation. Purge on deploy from deploy.sh.

Content-hashed assets expire after four hours

Medium

The stylesheet filename contains its own content hash, so it can never change under a given URL — but it's served with a four-hour TTL, forcing needless revalidation.

Evidence/assets/css/stylesheet.47e51c7d….css → cache-control: max-age=14400
Fixmax-age=31536000, immutable for /assets/css/ and /assets/js/. Leave images on a shorter TTL since their filenames aren't hashed.

The RSS feed carries all 350 posts

Medium

176 KB per fetch, re-downloaded by every reader on every poll.

Evidencepublic/index.xml → 350 <item>, 176 KB, description-only (183 chars average)
FixCap it with services.rss.limit: 30. Separately, consider whether to ship full post bodies via content:encoded — a 183-character teaser is thin for a feed reader.

Content 8 findings · 1 fixed

Editorial issues nothing in the current toolchain checks for.

Some posts displayed another article's title in their hero image

Fixed

49 cover images were shared between two or more posts, 35 of them named after one specific post. The initial estimate of 140 affected posts was from a script that only checked whether an image was shared and owner-named, not whether it actually had text rendered into it - the real number, after checking all 35 by eye, was smaller and worth being precise about.

WasConfirmed: ai-evals-are-broken.jpg rendered "Evaluating Agents in Production: Trajectory Metrics..."; context-engineering.png rendered "Context Engineering: The Discipline That Replaced Prompt Engineering" across 8 other posts.
Fixed

Installed tesseract to OCR-triage all 35 owner-named images at once rather than guessing from file size, then read each one to confirm - OCR on stylised sci-fi fonts over busy backgrounds is noisy enough that it's a triage signal, not a verdict on its own. Result: 17 images genuinely had another post's specific title or product name baked in (not 35) - the other 18 are generic concept art, diagrams, or category labels ("SUNO", "AI Cloud Subscriptions") that don't claim to be a different article, so reuse there is fine, same as the site's other big shared images.

For the 17 real ones, reassigned 47 borrowing posts to an already-established generic image in the same section (the site already had several safe, textless images shared broadly - music-production.png ×38, human-advancement-acceleration.jpg ×22 - so this extends that existing pattern rather than inventing a new one; no image generation involved). Alt text needed no changes - it already described each post's own content independently of what was literally in the image. Verified programmatically across the full rebuilt site (zero pages still show a problem image that isn't its own) and spot-checked visually.

One framing worth keeping. Almost everything above is either configuration or housekeeping. The writing, the tagging discipline, the internal linking and the editorial standards — the parts that are genuinely hard and genuinely slow to build — are already in place and in better shape than most sites this size. The gap is that the toolchain currently checks tags and orphan links, and nothing else. Most of these findings would have surfaced on their own if the same instinct that produced validate-tags.py were extended to frontmatter, images, headings and external links.
